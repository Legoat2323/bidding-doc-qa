# 招投标文件智能问答

把一份 332 页的工程招标文件，变成能问、能查、能指回页码的工具。

后端 FastAPI + LangChain + Chroma，模型用阿里百炼 qwen-plus，前端原生 HTML/JS。

## 这个项目解决什么问题

招标文件动辄两三百页，条款散在"投标人须知""评标办法""附件"好几个地方。同一件事
（比如"哪些情况会被废标"）正文提一句，详细列表在附件里。

投标方拿到文件后，要在两三天内回答四个问题：

1. 我们够格吗（资质、业绩门槛）
2. 投了会不会被废标（有 9 条否决情形，散在 p.50 和 p.72）
3. 报价怎么定（技术 25%、资信 40%、报价 35%，超限价直接废）
4. 中标后有没有坑（工期 360 天，违约责任怎么算）

漏看一条废标条款，几万到几十万的保证金和半个月的标书工作就白做了。这个项目
就是把这四个问题变成"点一下就能查"。

## 效果

两套题分开测，各管一件事：

| 题集 | 题数 | 用途 | 结果 |
|---|---|---|---|
| 开发集 `bid_eval.py` | 23（19 有答案 + 4 无答案） | 调参时反复跑 | 检索 **19/19**、回答 **19/19**、拒答 **4/4** |
| 忠实度（人工判定） | 18（有答案那 18 题） | 调参后复核 | **A 17 / B 1** → 忠实度 **17/18（94%）** |
| holdout `holdout.py` | 8（6 有答案 + 2 无答案） | 建好后没动过，只验收 | **8/8** |

忠实度看的是「回答里的每句话能不能在原文找到」，与「检索命中」是两件事。
`忠实度判定表.md` 里有 19 题的逐题判定与原文核对；两类失败形态不同——
**#4 是漏答**（只答 2% 上限、漏了 80 万硬顶）——已由覆盖层（`slots.py`）补上，现在会答「2% + 施工货物 80 万 + 服务类 10 万 + 本项目 50 万」。另：「履约保证金不予退还」曾被我判为「原文没有」移到 B 组当反例，**复核后发现 15.2.1 承包人违约情形里明确写了**（挂靠/转包/不履行合同 → 不予退还），已移回 A 组，B 组恢复 4 题全拒。

**为什么要两套**：23 题在调参过程中被反复看过（改 k、改分词、改提示词都对着它验），
100% 不能代表新题也准。holdout 是另外 8 道**从未参与任何改动**的题，它才对得上"换一批
文件还能不能答"。

延迟（`latency.py`，8 题 × 3 次，热身丢弃）：

| 召回宽度 | P50 | P95 | 候选数 |
|---|---|---|---|
| k=8 | 2.54s | 3.88s | 13 → 5 |
| k=32 | 2.65s | **3.17s** | 48 → 5 |

两组差异在测量噪声内——总延迟由两次 LLM 调用（改写 + 生成）主导，rerank 的边际成本被抖动淹没。
k=32 的真实代价在 token：送进 rerank 的 pair 从 13 涨到 48。

**基线冻结于 2026-11-21**：以上全部数字可用 `reproduce.cmd` 一键复现（单测 → 开发集 → holdout → 延迟）。
改代码、参数、题集后必须重跑，并在改动处注明日期——不要静默改数。

开发集覆盖的问题包括：

| 问题 | 正确答案 |
|---|---|
| 评分构成 / 权重 | J1=0.25、J2=0.40、J3=0.35（从表格正则抽取） |
| 否决投标情形 | 9 条，带页码 |
| 资格要求 | 营业执照、资质等级、类似业绩 |
| 投标保证金 | 缴纳规则、退还条件 |
| 投标有效期 | 90 天 |
| 总工期 | 360 日历天（设计 60 + 施工 300） |
| 最高投标限价 | 150,627,581.27 元 |
| 设计费 | 2,336,570.09 元 |
| 暂列金额 | 15,772,346.37 元 |
| 质量保证金比例 | 3% |
| 评标委员会人数 | 9 人或以上单数 |
| 项目经理需要什么证书 | 文件中未提及（诚实拒答） |
| 投标文件用什么字体 | 4 号仿宋 |

测试脚本在 `bid_eval.py`（开发集）和 `holdout.py`（验收集），可以自己跑。

## 技术上做了什么

### 1. 业务模板检索

用户说"价格占多少分"，招标文件写的是"投标报价权重 J3"。语义相近，字面完全不同，
向量和 BM25 都接不上，直接问就是"文档中未提及"。

解决办法是给高频问题预先写一句贴着文档用词的检索式：

```python
TEMPLATES = {
    "评分构成 / 权重": "权值构成 J1 J2 J3 技术方案权重 企业资信及履约能力 投标报价权重",
    "否决投标情形": "否决投标的情形 附件2-2 无效投标",
    ...
}
```

同一份文档、同一个意图，只因为用了文档里的词，召回从 0 变成有。

### 2. 表格数值用正则抽，不靠模型

评标权重藏在 PDF 的表格里，文字层抽出来是一堆碎片。用 embedding 检索不到，
让模型"读一下再告诉我"它会编。

所以这部分绕开模型，直接从检索到的原文里正则提取：

```python
WEIGHT_RE = re.compile(
    r"(技术方案权重|企业资信及履约能力|投标报价权重)\s*[Jj]?\s*([123])?\s*[（(]([^)）]*)[)）]\s*[:：]\s*([0-9.]+)"
)
```

抽出来是 J1=0.25 / J2=0.40 / J3=0.35，和原文一致。

**结论：结构化数据用代码查，别用 embedding 硬扛。**

### 3. 检索链路

```
问题 → 查询重写（qwen，温度 0.2，中文术语映射）
     → 混合召回（向量 k=32 + BM25 k=32，中文按 2-gram 切）
     → RRF 融合（去重 + 加权排名，约 48–56 条，不截断）
     → 重排序（gte-rerank-v2，top_n=5）
     → 相关性阈值过滤（默认关闭，0=关）
     → 拼 prompt → qwen-max
```

链路里每个数字都是测出来的，不是抄的：

| 参数 | 值 | 依据 |
|---|---|---|
| 召回 k | 32 | k=8 时正确答案排在 13 位，根本进不了 rerank（`exp_recall.py`） |
| BM25 分词 | 2-gram | 默认 `text.split()` 对中文等于失效，"评标委员会"成了一个词（`exp_bm25_tokenizer.py`） |
| 改写温度 | 0.2 | 0.7 时同一问题三种改写，评测噪声盖过真实改动 |
| 阈值 | 关闭 | 阈值只省上下文，不提准确率；且会误杀（`exp_threshold.py`） |

**已知未做**：改写只用改写后的查询，原问题被丢弃。实测"字面已经对得上"的问题，
原始问句检索排名比改写结果更好（`exp_noise.py`：1 vs 2），下一步可做双路召回。

课程原版还有一层 `LLMChainFilter`（逐条问模型"这段相关吗"），实测是 O(n) 次
串行调用，召回一加宽就卡十几分钟，收益有限，删掉了。

### 4. 相对课程原版的修复

| 文件 | 改动 | 原因 |
|---|---|---|
| `custom_loader.py` | 用 python-docx + pypdf 替换 unstructured | unstructured 依赖 langdetect（仅源码包）装不上 |
| `models.py` | 模型名改成实际可用的 ID | 课程写的 qwen-max-latest 已下线，返回 404 |
| `models.py` | 自实现 AliRerank | LangChain 自带 DashScopeRerank 漏传参数，返回空结果 |
| `models.py` | 加 timeout / max_retries | 不设超时会无限挂起 |
| `knowledge.py` | 中文查询重写 prompt | 课程用英文 prompt，对中文术语没用 |
| `knowledge.py` | 召回 k=3→32，重排 top_n=3→5 | 宽召回 + 窄精排（k=8 时正确答案排 13 位） |
| `knowledge.py` | BM25 中文 2-gram 分词 | 默认按空格切，中文整句成一个词，BM25 等于失效 |
| `knowledge.py` | 改写 prompt 收紧 + 温度 0.2 | 原 prompt 把"履约担保比例"扩成带"权重 计分"，且每次随机 |
| `config/settings.py` | `relevance_threshold` 默认 1.0 → 0.0 | 原值从未被读取（死配置），接上后 1.0 会把所有片段过滤光 |

## 前端

页面是手写的 HTML + 原生 JS，由 FastAPI 直接托管，没有用 Gradio。

原因：Gradio 的样式定制有上限（组件内部结构改不了），做不出产品形态。
现在 `web/` 下只有三个文件，没有构建链、没有 node_modules，改起来直接生效。

| 文件 | 作用 |
|---|---|
| `web/index.html` | 结构 |
| `web/style.css` | 样式（牛油果配色） |
| `web/app.js` | 请求 + 渲染（含一个 60 行的迷你 Markdown 渲染器） |

渲染器是自己写的，没引外部 CDN——离线部署也能用。

Gradio 版本（`bid_app.py`）仍然保留，作为备用调试入口，端口 7861。

## 作为服务使用（HTTP API）

```powershell
powershell -ExecutionPolicy Bypass -File .\run_api.ps1
```

打开 http://127.0.0.1:8000/docs 看自动生成的接口文档。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/health` | 健康检查（不需要鉴权） |
| GET | `/documents` | 已建索引的文档列表 |
| POST | `/ask` | 提问，返回答案 + 出处 + 事实校验结果 |
| POST | `/upload` | 上传文档并建索引 |

调用示例：

```bash
curl -X POST http://127.0.0.1:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"question": "投标有效期多久"}'
```

返回：

```json
{
  "answer": "投标有效期为自投标截止之日起90天（日历天）[p.277]",
  "sources": [{"ref": "p.277", "page": 277, "text": "..."}],
  "fact_check": {"checked": 1, "missing": []},
  "model": "qwen-plus",
  "doc": "招标文件正文22.pdf"
}
```

鉴权：在 `.env` 里设置 `API_KEY` 后，除 `/health` 外都要带 `X-API-Key` 头。
不设置则不校验（方便本地开发）。

## 踩过的坑

**1. 指标会骗人。** 第一次评估（当时只有 12 题）显示"检索 100%、回答 83%"，两条 ❌ 里有一条是
真实错误，另一条是我的关键词写窄了——文件里叫"投标担保"，不叫"保证金"。
后来把同义说法加进去，当时才是真实的 12/12。

**2. 中文分词：BM25 看起来在工作，其实没有。** 默认预处理是 `text.split()`，
中文整句被切成一个 token，"评标委员会"和"招标人"永远对不上。换成 2-gram（按相邻两字切）
之后，原来召不回的两道题当场回来了。**评估分数正常，不代表组件正常工作。**

**3. 评估集自己会过拟合。** 同一批题被改了十几次参数（k、分词、提示词、阈值），
分数必然越调越高。所以另建 8 道从未参与改动的 holdout，它才是对外的数。
更狠的一次：holdout 里有一题我判定"文档没有"，系统答出来了——原文写的是
"经会计事务所审计的财务报表"，我搜的是"审计报告"。**出题人的认知就是评估的天花板。**

**4. 关键词匹配不上 PDF 抽取的文本。** "投标截止时间"这题一度显示检索 ❌，
打出来看，原文是 `2023 -12-20 09:00`——PDF 抽取在年份和日期之间多了一个空格。
评估关键词是 `2023-12-20`，字符串搜不到。**判分脚本和被测系统一样需要被怀疑。**

**5. PDF 的表格抽不出来。** 投标保证金的具体金额在"投标人须知前附表"的表格里，
文字层抽出来是碎片，正则也抓不到。这是当前系统的真实盲区——扫描件、复杂表格
都处理不好。

**6. 改一处、忘一处。** 加工具时发现"知识库没资料就兜底"的判断写在调模型之前，
导致查天气永远返回"没有相关资料"。而且 `/chat` 和 `/chat_stream` 各写了一份，
只改了一处。正确的做法是抽成公共函数。

## 已知边界

- 只处理**文本层 PDF**，扫描件需要 OCR
- 一个项目一个知识库，不支持跨项目对比
- 不能自动写标书，只能查和答
- 模板检索式是人工写的，换一份格式差别大的招标文件要重新调整
- 表格抽取依赖正则，换排版会失效
- 一次提问两次 LLM 调用（改写 + 生成），P95 约 3.2s；要压延迟得缓存改写结果
- 召回加宽后送进 rerank 的 pair 从 13 涨到 48，token 成本约 3.7×，没做预算控制
- 改写会丢弃原问题，字面已经对得上的提问反而变差（`exp_noise.py`：原始问句排 1、改写排 2）
- 阈值过滤能接上但默认关闭：它只省上下文，不提升准确率，还会误杀
